# 功能疲乏（Features Fatigue）

## 定義

Kotler Ch08 在 Product Differentiation 9 維度中第 2 維「Features」上標註：

> "2. Features — Features fatigue — $400 億美金在 drop dead test" ^[extracted]
>
> — Kotler 16e Ch08 PSB Product, p.4

當廠商**不斷在加功能上競爭**，反而稀釋產品價值、增加複雜度、讓消費者疲乏，最終市場失敗。**Differentiation ≠ feature 最大化。**^[inferred]

## 觸發機制（為何發生）

Kotler Ch08 p.10 把 features fatigue 的根因歸納為三個（"Why less is more"）：^[extracted]

1. **Information overload** — 資訊過載
2. **Choice overload** — 選擇過載
3. **High consumer expectations** — 消費者預期過高

→ 結論：「**When less is more**」當減法勝過加法成為決策關鍵。^[extracted]

## 案例

| 公司 | 結果 | Kotler 解讀 |
|---|---|---|
| **HTC** | 機海戰術 fail | "Customized for vendors rather than end users!" ^[extracted] |
| **Nokia** | 失去王冠 | "當下 Priority 為堅固"（市場已轉向其他維度而 Nokia 停留舊維度）^[extracted] |
| **Apple** | 反例：成功 | "Apple Prioritize Features: simplicity" ^[extracted] |

> "目標市場的需求差異：並非所有客戶都追求最高規格的產品功能" ^[extracted from Kotler p.4 marginalia]

## 為何重要

Features fatigue 是**「加法策略」失效的訊號**。當市場處於成熟期，繼續加功能不會帶來新客戶，反而會：^[inferred]
- 增加製造成本
- 增加售後支援負擔
- 降低用戶體驗（功能太多反而難用）
- 讓品牌變成 commodity（誰功能多誰就贏的競爭）

→ Apple 的反例驗證了：**在所有人都加功能時，主動減功能可以變成 differentiation 本身**。^[inferred]

## 限制／適用邊界

- Kotler 未提 Roland Rust 等學者的 features fatigue 學術原始研究（Kotler PPT 只標記現象、沒引述出處）^[ambiguous]
- 非所有產品類別都適用 less-is-more — 耐久財／專業 B2B 工具可能需要功能廣度 ^[inferred]
- 觸發條件 Kotler 未量化（從何時 features 從加分變減分？）^[ambiguous]
